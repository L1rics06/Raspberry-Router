## 3. 核心技术产出

### 3.1 架构与调用链

```
用户 ──WS──> VPS 网关（分工2）──WS 出站──> 树莓派 Agent（分工3）
                                              │ ① 把工具清单交给 LLM
                                              │ ② LLM 决定调用 fan.set
                                              │ ③ MCP / JSON-RPC over stdio
                                     device_mcp_server.py（分工4）
                                              │ ④ GPIO / I2C
                                    LED / 风扇 / 继电器 / AHT20
```

MCP Server 由 Agent 按配置以 **stdio 子进程**拉起，Agent 通过 `tools/list` 自动发现工具，
通过 `tools/call` 执行；**加设备 = 加一个工具，Agent 代码零改动**。

### 3.2 对外暴露的 5 个工具

| 工具 | 参数 | 成功返回 | 硬件 | 高危 |
| --- | --- | --- | --- | --- |
| `led.set` | `on: bool` | `{"ok":true,"led":true,"detail":"..."}` | BCM17 | |
| `fan.set` | `state: bool` | `{"ok":true,"fan":true,"detail":"..."}` | BCM27 | |
| `relay.set` | `ch: int, state: bool` | `{"ok":true,"ch":0,"state":true,...}` | BCM5/6/13/19 | ⚠️ |
| `dht.read` | 无 | `{"ok":true,"temp":26.4,"hum":58.2}` | AHT20 / I2C | |
| `devices.status` | 无 | 状态快照 + `mode`/`pins`/`errors` | 调试用 | |

### 3.3 关键设计

1. **双后端**：`GpioBackend`（gpiozero + lgpio，Pi 5 兼容）与 `SimBackend`（内存态、温湿度漂移）。
   非 Linux / 无 gpiozero 自动仿真，也可用 `--sim` / `--gpio` 显式切换。
2. **配置外置**：引脚、有效电平、I2C 总线/地址全部走 `PIAGENT_*` 环境变量，改接线不改代码。
3. **故障隔离**：单个引脚初始化失败只禁用该设备，错误写入 `devices.status.errors`，其余工具照常。
4. **契约稳定**：工具名/参数/返回与冻结文档一致；返回永远是 JSON 字符串，异常不穿透协议层。
5. **工程细节**：stdout 只走 JSON-RPC、日志一律 stderr；`RLock` 串行化 GPIO/I2C；`atexit` 释放资源；
   兼容 MCP SDK 1.x（`FastMCP`）与 2.x（`MCPServer`）。
6. **安全分层**：Agent 侧工具白名单 + JSON Schema 校验 + `relay.set` 二次确认；设备侧通道越界校验；
   电气侧 3.3V 电平、共地、低压负载、不碰 220V。

### 3.4 默认接线（BCM）

| 设备 | BCM | 物理脚 |
| --- | --- | --- |
| LED（330Ω） | GPIO17 | 11 |
| 风扇继电器 | GPIO27 | 13 |
| 继电器 CH0-CH3 | GPIO5 / 6 / 13 / 19 | 29 / 31 / 33 / 35 |
| AHT20 SDA / SCL | GPIO2 / GPIO3 | 3 / 5 |

完整接线图与电气红线见 `devices/README.md` §5。

### 4.4 如何判断“真的成功了”

| 层级 | 怎么做 | 成功信号 | 说明 |
| --- | --- | --- | --- |
| L1 协议 | `mcp_selftest.py --sim` | `32 通过, 0 失败` + `✅ 仿真验收通过` | 只证明协议/契约正确 |
| L2 真机模式 | `mcp_selftest.py --gpio` | `mode` 为 `gpio`，且 `✅ 真机验收通过` | 证明 GPIO 真的被驱动 |
| L3 Agent 接入 | 重启 Agent | 日志出现 `MCP server 'devices' 已启动，工具: [...]` 与 `工具能力已上报` | 证明分工3 已发现工具 |
| L4 物理动作 | 控制台点 LED/风扇/继电器 | LED 亮灭、继电器“咔哒”、风扇转动 | 证明接线与负载正确 |
| L5 全链路 | `scripts/e2e_test.py` | `10 通过, 0 失败` | 证明用户→VPS→Pi→硬件全通 |
| L6 远程演示 | 手机关 WiFi 用 4G 发指令 | 寝室硬件动作 | 最终验收 |

**三个常见“假成功”**：

1. `mode` 是 `sim`：跑的是仿真，代码没碰 GPIO；
2. 继电器有“咔哒”声但负载不转：负载电源 / COM-NO 接线问题，不是 MCP 问题；
3. 工具返回 `ok:true` 只代表 Server 接受了调用，**不代表线接对了**——要配合 L4 的物理观察。

> 还没接温湿度/继电器时，可用 `--gpio --skip-dht --skip-relay` 先验收其余部分；
> 跳过的项显示 `⏭️`，不算失败，但最终验收要补跑全量。

### 4.5 验证边界（如实说明）

- 仿真验证的是“协议、契约、Agent 集成”正确，**不能证明接线与 GPIO 驱动正确**；
- 真机自检 `--gpio` 与 VPS 全链路 `e2e_test.py` 尚未执行，已列入待办。

## 7. 汇报/答辩要点

1. **MCP 是 AI 世界的 USB-C**：统一“能力描述 + 调用”协议，把 M×N 适配变成 M+N，所以换硬件不用改 Agent。
2. **我的核心产出是“设备工具化”**：5 个工具覆盖执行器与传感器，加设备只是加一个 `@mcp.tool`。
3. **用协议级自检证明可用**：32 项断言 + 分工3 客户端零改动联调，而不是“看起来能跑”。
4. **边界清晰**：软件契约已验证，真机接线仍需上板验收——不把仿真当真实。
