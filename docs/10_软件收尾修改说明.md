# 本次软件收尾修改说明

下面逐项按问题、位置、前后方案、思路、理由、作用和验证说明

## 1. 聊天方向与实际执行校验

1. 当前问题：旧检查只看actions字符串包含light.set，两条聊天均执行on=false仍可能通过
2. 修改位置：task4/gateway_checks.py的validate_chat_trace、validate_chat_effect、run_gateway；tests/test_acceptance.py
3. 修改方案：修改前为字符串包含检查；修改后逐条解析精确工具名与JSON参数，开灯只能为布尔true、关灯只能为布尔false，每条恰好一次按压；前后状态必须显示command_count恰好增加1，requested_on匹配
4. 整体思路：工具轨迹检查“要求做什么”，独立devices.status检查“设备是否执行了相同目标”；两者都通过才通过聊天验收
5. 修改理由：模型说成功、工具名存在、布尔方向正确、实际执行正确分别是不同的事实，不能互相代替
6. 好处和作用：能拒绝相反方向、数字/字符串布尔、重复字段、额外参数、未知工具、重复按压，以及只有轨迹没有动作的情况
7. 注意事项和验证：回归用完整run_gateway路径复现错误方向、未执行和状态相反，均返回FAIL且不重发；正确场景通过，真实灯光仍由现场观察

## 2. 合并状态保留旧设备错误

1. 当前问题：原合并入口把LED等错误只放在other_devices.errors，顶层errors可能为空
2. 修改位置：devices/wall_light_mcp.py的merge_status及devices_status；tests/test_acceptance.py
3. 修改方案：修改前只复制led/fan/relay/pins；修改后同时保留原顶层errors、原始快照及other_devices_ready，舵机错误重名时逐层添加servo前缀
4. 整体思路：先复制原错误，再加入舵机错误，绝不覆盖原键；原设备ok=false或errors类型错误也要显式保留故障
5. 修改理由：原接口客户端依赖顶层errors，新增嵌套对象不能替代原字段语义
6. 好处和作用：旧客户端能发现原外设故障，舵机ready和其他外设状态可分别判断，任一来源状态均不被原地修改
7. 注意事项和验证：覆盖健康、LED错误、舵机错误、键冲突、原状态失败和畸形errors；合并入口仍通过原32项仿真契约，原设备真机接线仍需现场检查

## 3. E2E接口、目标与证据门槛统一

1. 当前问题：原仓库E2E调用不存在的servo.set(angle=45)，自动挑选首台在线设备，旧聊天证据不足
2. 修改位置：scripts/e2e_test.py、task4/evidence.py、local_demo.py及仓库接口文档
3. 修改方案：修改前用位置参数传PAT、固定角度工具及弱轨迹；修改后用明确profile/device_id、环境变量PAT、light.set(on:bool)，默认只读，--actuate才动作，--chat必须配合动作选项
4. 整体思路：E2E复用同一个run_gateway验收器，减少接口漂移；本机demo实际启动网关和Agent后通过子进程运行新版E2E，证据检查还要求方向和设备计数标记
5. 修改理由：测试程序必须调用当前真实接口，且不能误动其他设备，旧弱报告不能作为新版现场验收依据
6. 好处和作用：用户可沿用原scripts/e2e_test.py入口，失败不自动重发，报告同时核对外层与设备内层ok
7. 注意事项和验证：本机新版E2E实际执行通过，50项完整链路检查同时包含非法参数、失败传播、聊天失败、离线503和重启无动作；真实模型与公网仍需现场联调

## 4. 独立包与原仓库布局集成

1. 当前问题：独立上机包的网关/Agent路径与原仓库不同，直接复制会保留旧模板及失真的SG90说明
2. 修改位置：task4/layout.py、deploy.py、local_demo.py、原仓库Agent模板、README、设备说明、工具契约及搭建/成果文档
3. 修改方案：修改前固定依赖snapshot与runtime_source路径；修改后原仓库优先使用根目录server/agent和devices，独立包使用附带的基线及修复版Agent，Agent示例明确默认模拟模式
4. 整体思路：集中解析三个实际源码位置，保留旧五工具和基线以便复现；修改仅涉及设备实现、配套Agent错误传播、测试与说明，不改VPS或前端业务
5. 修改理由：交付必须在两个布局中运行一致，上层看到的软件状态不能超过实际验证证据
6. 好处和作用：可直接独立上机，也可应用一个完整补丁集成回原仓库，原其他模块代码保持可协作状态
7. 注意事项和验证：54个上游文本Git对象逐个匹配；集成布局另跑完整软件检查，补丁在全新基线上检查、应用并逐字节核对；原仓库后续有修改时先git apply --check
