舵机驱动、机构标定工具、墙灯MCP、部署和验收程序均已提供；前次发现的两处验收/兼容性缺口已修复。86项单元测试、50项本地链路检查通过，真实设备运行仍需接线后验证

你先在Pi离线完成本地标定和开/关测试，再接整个项目的三个模块

| 项目分工 | 对方提供什么 | 你提供什么 |

## 给分工3的具体接入

默认由prepare-agent生成完整配置和独立服务；独立包使用 `runtime_source/agent/`，仓库集成版使用根目录 `agent/`，两处Agent修复均已包含，设备ok=false和MCP isError不会被显示成成功

如果分工3希望继续使用原Git仓库的Agent，将 `integration_patches/Agent错误传播修复.patch` 交给他；先在原仓库检查补丁，确认与其当前改动无冲突后合并，不直接覆盖他的未提交工作

新增MCP服务配置对应：

```toml
[[mcp.servers]]
name = "wall-light"
command = "/实际路径/交付包/.venv/bin/python"
args = ["/实际路径/交付包/devices/wall_light_mcp.py", "--gpio", "--config", "/实际路径/交付包/configs/servo.local.toml"]
env = { PYTHONUTF8 = "1", PIAGENT_MCP_SIM = "0" }
```

该服务提供light.set和devices.status，现有Agent如果还启动原设备服务，会与devices.status重名；本包运行版会明确拒绝，不再悄悄覆盖

需要同时控制原来的LED、风扇、继电器和温湿度时，**只启动一个合并入口** `devices/all_devices_mcp.py`，或者给wall_light_mcp加 `--with-existing-devices`

合并后的6个工具为light.set、led.set、fan.set、relay.set、dht.read、devices.status；原有工具的参数和返回字段沿用上游，统一状态中附加other_devices和舵机字段

对应配置模板是 `profiles/combined-hardware.example.toml`。它会允许全部6个工具，但relay.set仍需要手动confirmed确认，聊天不应执行继电器

只做本次舵机项目时使用默认hardware.local.toml，不加载其他设备、GPIO库或I2C

## 原有设备合并的可选依赖

直接硬件PWM控制舵机不需要gpiozero、lgpio、pigpio或RPi.GPIO

合并原设备时，按原设备驱动需要安装gpiozero、lgpio、smbus2，并启用对应I2C；这属于可选外设接线测试，不能在没有外设时声称真机通过

可在Pi的同一个虚拟环境中安装：

```bash
.venv/bin/python -m pip install 'gpiozero>=2,<3' 'lgpio>=0.2,<1' 'smbus2>=0.4,<1'
```

这些可选GPIO依赖本次未在Pi ARM上安装验证，默认舵机方案不依赖它们

原LED默认BCM17、风扇BCM27、继电器BCM5/6/13/19；这里的BCM6是物理31脚，与共地所用物理6脚不是同一个编号

## 给分工1的网页接入

开灯：工具light.set，参数 `{"on":true}`

关灯：工具light.set，参数 `{"on":false}`

查状态：工具devices.status，参数 `{}`

当前上游主前端已有通用工具JSON输入卡，light.set即使没有专用按钮也可以输入上述参数执行；不要使用原servo.set的0/90/180度按钮控制这套机构

必须使用用户选定设备的device_id，不自动挑选第一台在线设备。展示“按压流程完成”，lamp_state=unknown时不显示“已检测到灯亮”

如果采用旧调试页，其自动选择首台设备的逻辑不能用于多设备实测，优先使用主前端或本包明确设备ID的gateway-check

## 给分工2的核对项

dev令牌绑定这台Pi和正确owner，pat令牌属于有权限的访问者；两者不能互换

如地址带/piagent前缀，HTTP和WS都应保留该前缀转发。服务端模型配置需要能处理工具调用，本机规则demo不验证真实模型质量
